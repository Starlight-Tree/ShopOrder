# 分析（売上・在庫・配達・顧客）

テーブルは [data-model.md](data-model.md)、動きは [order-flow.md](order-flow.md)。この規模（12 店・ダミーデータ）は **Postgres だけで足りる**（設計判断。規模は未計測）。別基盤（BigQuery など）は使わない。調査の出どころ: Postgres・BigQuery の公式文書（2026-11-21、Workflow の調査。指標の定義・ABC・RFM の書き方は一般知識）。

## 作り方

1. 注文系の正規化テーブルに `(business_date, 店, 品目, カテゴリー, 受け取り方法)` の索引を張り、**通常のビュー**から始める。
2. 重くなったら、**日次集計表**（確定した日だけを upsert。当日は元データから都度計算して `UNION`）にする。マテリアライズドビューを使うなら、必ず `UNIQUE` 索引を付けて `CONCURRENTLY` で更新する。
3. 分析の読み取りは `analytics` スキーマに集約し、画面の API は集計表を読むだけの薄い層にする。将来、別基盤へ移すときは、その集計表を日次で出すだけで済む形にする。
4. **営業日（`business_date`）:** 店ごとの締めで決める。UTC や端末の日付に依存しない。欠測日は、営業日カレンダー（定休日 + `store_closures`）と `generate_series` で補い、「休業（NULL）」と「営業したが売上 0」を区別する。ザーハードの 1 日の長さ・曜日の扱いは、店舗案内が 24 時間制・月〜日で書いているのに従う（惑星固有の暦は設定しない。未決）。
5. **メトリクス辞書**（`docs/metrics.md`。実装のときに作る）: 指標の定義を 1 か所に書き、集計 SQL と画面の説明文が同じ定義を参照する。

## 画面とグラフ（店長・店舗スタッフ）

すべてのグラフに「**表で見る**」切り替えを付け、色の凡例だけで意味が決まらないようにする。グラフの種類は最小限。

| 画面 | 中身 | 形 |
|---|---|---|
| 今日の概況 | 売上・注文数・客単価・配達中の件数 | タイル 4 つ |
| 売上の推移 | 日・週・月。前期比（期間の長さと曜日構成がそろうときだけ。足りなければ「比較不可」） | 折れ線 + 移動平均 |
| 商品別 | 売上・杯数・構成比、ABC（累積 80% / 95%） | 横棒 + 表 |
| 曜日 × 時間帯 | 注文数 | ヒートマップ（HTML の表 + CSS 変数の色の段階） |
| 受け取り方法 | 店頭 / 宅配の比率と推移 | 積み上げ面 |
| 在庫 | 残日数・発注点との差・廃棄の量と理由・原価率（差異ロスつき） | 棒 + 表 |
| 配達 | 受付から到着までの所要時間 p50 / p90、不在率、枠の埋まり具合 | 折れ線・表 |
| 顧客 | RFM の分布、初回月 × 経過月のコホート、再購入率、LTV の目安、離脱の兆候 | 棒・表（コホートは HTML の表） |

- ライブラリは shadcn/ui の Chart（Recharts v3）。管理画面は顧客の画面と別のルートにして**動的 import**（顧客の初期表示に影響させない。採用前にビルドのバンドル解析で計測する。未確認）。
- 色は CSS の変数だけ。ライトとダークの両方に定義し、文字は WCAG AA（4.5:1）。

## 顧客データの分析

- **既定は集計だけ。** 分析画面は店長ロールだけ。個別の顧客に降りる画面は、権限と操作履歴つきの別画面にする。
- **仮名 ID:** 分析スキーマには、秘密の鍵を使った HMAC の仮名 ID だけを置く。氏名・住所・電話・自由記述は入れない。鍵は別管理。
- **最小の集計単位:** 5 人未満のセルは出さない（コホート表で特に）。ダミーの顧客が少ないときは、固定の閾値（例: R = 30 日以内）を既定にし、分位は選択式にする。
- **利用目的:** 画面（プライバシー）に、「注文の履行・配達の連絡・購買履歴の分析による商品提案と店の改善」と具体的に書く。
- **共起によるおすすめ（機械学習なし）:** `order_items` の自己結合の集計 SQL で足りる。JobNavi の閲覧記録・おすすめの作りが参考。
- **退会・保存期間:** 個人項目だけ消して、注文の数値は残す（匿名化）。

本物の個人情報の法令（個人情報保護法）は、架空の世界のダミーには及ばない。ただし**実在の店に切り替えても作り直さない**ように、上の作法を最初から入れる（調査: 個人情報保護委員会の公開資料、2026-11-21）。

## データ（ダミー）

売上・在庫・顧客の分析には、現実的なダミーが要る。seed で次を**固定の乱数の種**から作る（同じ結果になる）。

- 12 店（world.md）、メニュー 14〜18 品、配達区画 4、配達員 6〜8、顧客 60〜120 人。
- 過去 90〜120 日の注文。曜日・時間帯の波（朝と夕方が多い）、店ごとの規模（席数に比例）、看板（OB）の比率、季節の切り替え日・帰還祭（12/1〜12/25）の山、宅配の比率（新設の機能なので、開始日以降だけ）。
- すべてダミーであることを、seed の冒頭と画面に明記する。**資料の事実（店・席・営業時間）と、ダミーの数字（売上・顧客）を混ぜない。**

## 公開しないもの

売上・顧客の分析の API と画面は、店長（全店）と店舗スタッフ（自店の売上・在庫のみ）に限る。顧客・配達員には見せない。
