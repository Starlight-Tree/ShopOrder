# メトリクス辞書（分析の指標の定義）

指標の定義を **1 か所**に書く。集計の SQL（[backend/app/analytics_build.py](../backend/app/analytics_build.py)・[analytics_queries.py](../backend/app/analytics_queries.py)）と画面の説明文は、ここを参照する。数字の閾値は [analytics_rules.py](../backend/app/analytics_rules.py) の 1 か所にあり、変えるときは、そこと この文書を一緒に直す。
作り方・画面・顧客データの作法は [analytics.md](analytics.md)、表は [data-model.md](data-model.md)、API は [api.md](api.md)「分析（P4）」。

**範囲（2026-11-21）:** 店頭受け取り（P1）の注文だけ。宅配（P2）の指標（受け取り方法の比率・所要時間・不在率）は、P2 の後。通貨はルミ（整数。world.md）。データはすべてダミー。
閾値（14 日・80%・5 人など）は、設計の既定で、実測ではない。

## 共通の決まり

| 用語 | 定義 |
|---|---|
| 営業日（`business_date`） | 注文を受けた店の、ローカル時刻の日付（`orders.business_date`）。UTC や端末の日付に依存しない。ローカル時刻は `LOCAL_UTC_OFFSET_HOURS`（既定 9）。惑星固有の暦は設定しない（world.md） |
| 確定した日 | 営業日が今日より前の日。日次集計表には、確定した日だけを作る。**当日は、元データから都度**（API が読む） |
| 営業日カレンダー | `analytics.store_days(from, to)`。店 × 日付 → 営業日か。定休日（`stores.closed_weekday`）と臨時休業（`store_closures`）から作る。**completed か cancelled の注文がある日は、カレンダーが休みでも営業日にする**（実際に開けた日。売上を捨てない） |
| 休業 と 売上 0 | 休業日は、集計表に行を作らず、API は **null**（グラフは線が途切れ、表は「休業」）。営業日は売上 0 でも `daily_store_summary` に行を作り、API は **0**。営業日なのに行が無い日は「未集計」（null。0 にしない） |
| MO 不可の店 | 居住区信号塔店（world.md）は、注文アプリで注文できないので、営業日でも売上は 0 になる。**この分析の売上は、このアプリの注文（店頭受け取り）だけで、店の全売上ではない** |
| 最小の集計単位 | **人数を数えるセル**（顧客の区分・R×F・コホート・再購入率）は、**5 人未満を出さない**（`null`。画面は「5 人未満」）。0 人のセルは 0。隠したセルが 1 つだけのときは、合計から引き算で戻せるので、残りで最小のセル（5 人以上）も隠す。隠したセルがあれば、顧客の合計も出さない。注文の件数・売上（人数でないセル）には、この規則を適用しない |
| 仮名 ID | 顧客は、秘密の鍵（環境変数 `ANALYTICS_PSEUDONYM_KEY`）の HMAC-SHA256 の先頭 128 ビット。`analytics` には、氏名・メール・住所・自由記述を入れない。仮名 ID と `users.id` の対応（`customer_pseudonyms`）は、集計の作成だけが読み、API は読まない。退会のときは、この対応の行を消す（数値は残り、誰のものか辿れなくなる）。鍵が前回と違うと、集計の作成は止まる（`--rekey` で顧客の表を作り直す） |

## 売上・注文

| 指標 | 定義 | 出どころ |
|---|---|---|
| 売上（ルミ） | `status = 'completed'` の注文の `total_lumi` の合計（送料を含む。いまは店頭だけなので送料 0）。取消し・進行中は入れない | `daily_store_summary.sales_lumi`、当日は `analytics.order_facts` |
| 注文数 | completed の件数。取消し（cancelled）は別に数える（`cancelled_orders`） | 同上 |
| 客単価 | 売上 ÷ 注文数（四捨五入。注文が 0 なら null）。期間の客単価は「期間の売上 ÷ 期間の注文数」（日ごとの平均の平均にしない） | 計算 |
| 杯数 | 区分が `drink` の品の数量の合計（サイズ・温度を束ねる） | `daily_store_item_sales`（`category = 'drink'`） |
| 対応中の注文 | 今日の営業日で、状態が paid / accepted / preparing / ready（と宅配の assigned / picked_up / delivering）の件数。`placed`（支払い待ち）は入れない | `analytics.order_facts` |
| 前日の値 | 概況のタイルに添える。日次集計から読む（休業は「休業」、未集計は「未集計」） | `daily_store_summary` |
| 移動平均 | 直近の窓（日: 7 点、週: 4 点、月: 3 点）のうち、**値のある点（営業日）だけ**の平均。休業・未集計の点を 0 として混ぜない。値のある点が 3 点（窓が 3 未満なら窓の数）そろうまでは出さない | 画面（`movingAverage`） |
| 前期比 | 期間（日: 昨日まで N 日、週: 昨日までに終わった N 週〔月〜日〕、月: 昨日までに終わった N か月）の売上を、**直前の同じ長さの期間**と比べた変化率（小数 1 位）。**比べるのは次がすべて満たされるときだけ。足りなければ「比較不可」（理由つき）**: ① 前の期間の営業日が全部集計済み（`previous_missing`）② 期間の長さと曜日の構成が同じ（`weekday_mismatch`。日は 7 の倍数でそろう。月は、ほとんど比べられない）③ 営業日（店 × 日）の数が同じ（`open_days_mismatch`。休業があると比べない）④ 前の期間の売上が 0 でない（`previous_zero`） | `analytics_rules.comparison` |

## 商品

| 指標 | 定義 |
|---|---|
| 品目 | `menu_items` の単位（サイズ・温度は束ねる）。名前・区分は集計時の写し |
| 構成比 | その品の売上 ÷ 期間の全品の売上 × 100（小数 1 位） |
| 累積構成比 | 売上の大きい順（同額は ID 順）に、構成比を足し上げたもの |
| ABC | **その品の手前までの累積**で決める。80% 未満なら **A**、95% 未満なら **B**、それ以外は **C**。80% をまたぐ品は A に入る（A が空にならない）。売上が 0 の期間は、すべて C |

## 曜日 × 時間帯

注文数 = completed の件数を、営業日の曜日（ISO: 月 = 1 … 日 = 7）× **店のローカル時刻の時**（受付 `placed_at` の時）で数える（期間内の合計）。`store_days` は、その曜日の営業日（店 × 日）の数。ヒートマップの色の段階は、最大のセルに対する割合を 5 段階に切り上げたもの（0 件は 0 段階）。

## 在庫

| 指標 | 定義 |
|---|---|
| 残量 | 今の残高（`stock_balances`。当日を含む）。日次の締めの残量（`daily_stock_levels.on_hand_end`）は、台帳（receive・consume・waste・adjust）から再計算した、その日（ローカルの 24 時）の値 |
| 1 日の消費 | 直近 14 営業日の `consumed`（台帳の consume の符号を反転）の合計 ÷ その営業日の数 |
| 残日数 | (残量 − 確保中) ÷ 1 日の消費（小数 1 位）。消費が 0 なら null（画面は「消費なし」）。全店のときは、**最も厳しい店の値** |
| 発注点との差 | 出せる量（残量 − 確保中 − 安全在庫）− 発注点。負なら発注点を下回る（`low`。API の `low` と同じ定義）。全店のときは、最も厳しい店の値と、下回る店の数 |
| 廃棄の量 | 直近 30 日の waste の合計（品目ごと。単位が品目で違うので、品目をまたいで足さない） |
| 廃棄の率 | 廃棄 ÷ (消費 + 廃棄) × 100（直近 30 日） |
| 廃棄の理由 | 台帳の理由は自由記述なので、**固定の 4 区分**に写す: 期限切れ（期限・賞味・消費）/ 破損（破損・落と・こぼ・割れ）/ 品質（品質・鮮度・味・劣化）/ その他。自由記述そのものは `analytics` に持ち込まない |
| 休業日の動き | 在庫の日次の行は営業日だけ。休業日の入荷・廃棄は、その日の行には出ないが、残量（`on_hand_end`）には入る |
| 原価率 | **未実装**（原価の列が無い。ロットと単価を入れるとき） |

## 顧客（RFM・コホート）

期間は、今日の手前の 90 日（確定した日）。completed の注文だけ。

| 指標 | 定義 |
|---|---|
| R（新しさ） | 最後の注文から今日までの日数。14 日以内 = 3、15〜30 日 = 2、31 日以上 = 1 |
| F（回数） | 期間内の注文数。30 回以上 = 3、10〜29 回 = 2、9 回以下 = 1 |
| M（金額） | 期間内の利用額。20,000 ルミ以上 = 3、8,000 以上 = 2、それ未満 = 1（区分には使わず、保存する） |
| 区分 | R=3 かつ F=3 **常連** / R=3 かつ F=2 **通い** / R=3 かつ F=1 **ときどき** / R=2 **離れかけ**（離脱の兆候）/ R=1 **休眠**。ダミーの顧客が少ないので、分位ではなく固定の閾値にする（analytics.md） |
| 再購入率 | 期間内に 2 回以上注文した顧客 ÷ 期間内に注文した顧客（小数 1 位）。**1 回だけの顧客と 2 回以上の顧客の両方が 5 人以上のときだけ**出す（片方が 5 人未満だと、人数が逆算できるため） |
| 1 人あたりの利用額（LTV の目安） | 期間内の利用額の合計 ÷ 顧客数（四捨五入）。顧客が 5 人以上のときだけ。生涯価値の予測ではなく、期間内の実績の目安 |
| 離れかけの顧客 | 区分が「離れかけ」の人数（5 人未満は出さない） |
| コホート | 初回月 = その顧客の最初の注文の月（全期間）。経過月 = 注文した月 − 初回月。セル = その月に注文した人数 ÷ 初回月の人数（割合）と人数。5 人未満のセルと、初回月の人数が 5 人未満の行は出さない。**当月は途中**（確定した日まで）。データの最初の月の行は、データの開始前から来ていた人を含みうる（`includes_existing`） |

## 集計表と指標の対応

| 表（`analytics`） | 粒度 | 主な列 | 使う指標 |
|---|---|---|---|
| `daily_store_summary` | 店 × 営業日 | orders・cancelled_orders・sales_lumi | 売上・注文数・客単価・前期比・休業と 0 の区別 |
| `daily_store_item_sales` | 店 × 営業日 × 品目 × 受け取り方法 | qty・sales_lumi・category | 商品別・ABC・杯数 |
| `daily_store_hourly` | 店 × 営業日 × 時間 × 受け取り方法 | orders・sales_lumi | 曜日 × 時間帯 |
| `daily_stock_levels` | 店 × 営業日 × 在庫品目 | on_hand_end・received・consumed・wasted・adjusted | 1 日の消費・残日数・廃棄の率 |
| `daily_stock_waste` | 店 × 営業日 × 品目 × 理由 | qty | 廃棄の量と理由 |
| `customer_pseudonyms` | 顧客 | user_id ↔ 仮名 ID | （作成だけが使う。API は読まない） |
| `customer_rfm` | 仮名 ID | orders・spend_lumi・recency_days・r/f/m_score・segment | 区分・再購入率・利用額の目安 |
| `customer_monthly` | 仮名 ID × 月 | orders・spend_lumi | コホート |
| `build_state` | キー | 鍵の指紋（鍵そのものではない） | 鍵の変更の検出 |

読み取りのビュー: `analytics.order_facts`（注文の事実。個人を含まない）・`analytics.sales_lines`（completed の明細）・`analytics.stock_position`（今の残高）。集計の作成と当日の読み取りが、同じ定義を使う。

## まだ無い指標

- 受け取り方法の比率と推移（積み上げ面）、配達の所要時間 p50 / p90・不在率・枠の埋まり具合: 宅配（P2）の後。表（`fulfillment` 列・`daily_delivery_stats`）の置き場は設計に入れてある。
- 原価率（差異ロスつき）: 原価の列が無い。
- 共起によるおすすめ・個別の顧客へ降りる画面（権限と操作履歴つき）: P5。
