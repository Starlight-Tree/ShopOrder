# 注文・在庫・配達の流れ

テーブルは [data-model.md](data-model.md)。世界観の値は [world.md](world.md)。ここは動きの決まり。数字（15 分・30 分・5 回など）は設計の既定で、設定値にする。資料に書かれた事実と、新設の設定を区別して書く。

## 注文の状態

```
cart(下書き) ─確定ボタン→ placed ─支払い→ paid ─店が受ける→ accepted ─調理開始→ preparing ─→ ready
                                                                                     │
        受け取り（店頭）: ready ─渡す→ completed                                       │
        宅配:  ready ─割り当て→ assigned ─集荷→ picked_up ─出発→ delivering ─→ delivered → completed
                                                                      └ 不在 → delivery_failed ─再配達 / 取消し
  どこからでも（条件つき）: cancelled / refunded
```

| 遷移 | 誰が | 条件・副作用 |
|---|---|---|
| cart → placed | 顧客（確定ボタン） | `checkout_proposal` が有効（カートの版・合計・期限が一致）。営業時間・ラストオーダー・MO 不可店・配達区画・時間枠・在庫を**再検証**。在庫を確保（`reserve`）。冪等キー必須 |
| placed → paid | 支払いの提供者（模擬は即時） | 失敗・期限切れ（既定 15 分）で確保を戻して `cancelled`。ポイント付与は completed のとき |
| paid → accepted | 店（スタッフ） | 受けられない（材料切れ・閉店）なら理由つきで cancelled → 返金 |
| accepted → preparing | 店 | レシピの原材料を `consume`。確保した分を消費に変える |
| preparing → ready | 店 | 店頭は「準備完了」を通知。宅配は配達員の割り当て待ち |
| ready → completed（店頭） | 店 | 受け取りは**注文から 30 分以内**（派生資料の記述で、正本には無い。派生資料どうしも、期限切れの返金の扱いが食い違う）。期限を過ぎた注文は、取消し・返金するかを**店長が判断**する（新設）。ポイント付与 |
| ready → assigned | 店（手動）または提案の採用 | 配達員の提案は区画間の所要時間の最小。配達員が自分で受ける方式（`SKIP LOCKED`）は後 |
| assigned → picked_up → delivering | 配達員 | 集荷時に暗証コードが顧客に見える |
| delivering → delivered | 配達員 | **暗証コード**（4 桁）が合うこと。写真は任意（置き配）。5 回間違えると凍結して店へ |
| delivering → delivery_failed | 配達員 | 不在・受け取れない。理由を記録。再配達（枠の上限の対象）か取消し |
| ＊ → cancelled | 顧客（paid まで）/ 店 / 店長 | 顧客は accepted より前だけ。以降は店に連絡（チャット・スレッド）。確保・枠を戻す。返金は `payments` を `refunded` に |

許されない遷移は 409。遷移ごとに `order_events` へ（誰が・いつ・理由）。**注文の状態は画面が API の最新から描く**（履歴の文言を信用しない）。

## 注文の確定（place_order）

1 つの DB トランザクションで、次を順に行う。途中で失敗すれば全部戻る。

1. 冪等キーを `idempotency_keys` に INSERT（既にあれば保存済みの応答を返す。内容が違えば 422）。
2. `checkout_proposals` を検査して使用済みにする（版・合計・期限）。
3. カートの再検証（価格を `menu_variants` の今の値で再計算し、提案の合計と違えば拒否。営業時間・ラストオーダー・MO 不可店・品揃い）。
4. **在庫の確保:** 原材料ごとに `UPDATE stock_balances SET reserved = reserved + :n WHERE ... AND on_hand - reserved - safety_stock >= :n`。更新 0 行なら在庫不足（`CHECK` が最後の砦）。ロットを使うものは、品目 → 期限 → lot_id の**固定順**で `FOR UPDATE`（デッドロック防止。`40P01` と `40001` は再試行）。台帳に `reserve` を追記。
5. 宅配なら、時間枠を `UPDATE delivery_slots SET booked = booked + 1 WHERE booked < capacity` で確保。区画・最低注文額・送料を検査。
6. `orders`・`order_items`（単価・名前のスナップショット）・`payments(pending)`・`stock_reservations` を作り、`order_events` に追記。

**確保のタイミングは、カートに入れた時ではなく、確定の時。** 支払いまでの期限つき（既定 15 分）。期限切れは worker が戻し、アクセス時にも遅延で戻す（worker が止まっても在庫が固まらない）。

## 在庫の操作

| 操作 | 誰が | 台帳の種別 |
|---|---|---|
| 入荷（工房から。豆は金・土の午前 = 資料） | スタッフ | `receive`（ロット・賞味期限つき） |
| 調理開始で消費 | 自動 | `consume`（確保を消費へ） |
| 廃棄（期限切れ・失敗） | スタッフ | `waste`（理由つき） |
| 棚卸し | スタッフ | `adjust`（差異を調整行として足す。履歴は書き換えない） |
| 発注点の警告 | 自動 | `available < reorder_point` で店長へ通知 |

賞味期限・焙煎日は豆と菓子だけ（最初は）。除去日（賞味期限 − N 日）を過ぎたロットは引当て対象から外し、廃棄候補に出す（N は設定値。新設）。原価は、最初に**ロット別の仕入単価**に決める（FEFO と整合）。

## 宅配

- **区画と送料（新設）:** 4 エリア = 4 区画。送料は区画ごとの基本料 + 一定額以上で無料（Shopify 型。調査: 公式文書、2026-11-21）。区画ごとに最低注文額・基準の所要分。店は、自分のエリア + 隣接 1 エリアへ届ける。
- **時間枠:** 30 分枠・上限件数。受付締めは「準備時間 + リードタイム」。休業・嵐の警報（区画の `is_suspended`・`store_closures`）では枠を出さない。
- **配達員:** 浮上スクーター（新設）。割り当ては、最初は店が画面で選ぶ + 区画間の所要時間による最寄りの提案。割り当ての方針は差し替え可能な関数にしておく（巡回の最適化は後）。
- **受け渡し:** 暗証コード（4 桁・ハッシュ・5 回で凍結・完了か 24 時間で失効）。写真は任意で、保持は短く（既定 30 日）、見られるのは店長と当該注文の関係者だけ。
- **配達の所要時間** は `order_events` の時刻から計算する（p50・p90）。
- **模擬の配達:** 開発の既定は `DeliveryProvider=mock`。worker が時間経過で `delivering → delivered` まで進める（実在の事業者への差し替え口は残す）。

## 世界観との接点（新設。確定した設定ではない）

- 屋外は大気が薄く寒暖差が大きい。配達員は酸素・保温の装備で動く。**砂嵐の警報**は、店長が区画ごとに立てられ、枠の受付を止める（砂嵐の設定は資料に無い。設計で足す）。
- アルカ市内の道が屋外か屋内かは資料に無いので、画面は「配達中」までを出し、道の描写はしない。
- MO（モバイルオーダー）は資料にある（アプリで事前に注文・支払い、店のカウンターで受け取り）。居住区信号塔店だけ不可。**宅配は資料に無い新機能。**

## 通知（アプリ内。既定）

イベント（受付・調理開始・準備完了・集荷・配達中・到着・完了・取消し）から `Notifier` が作る。既定はアプリ内の通知欄 + 画面の更新。Web Push・メールは後（差し替え口）。LINE は対象外。

## 状態（2026-11-21）

**P1 の店頭受け取りの流れ（確定・支払い・取消し・スタッフの遷移・期限切れの戻し・在庫の確保と消費・ポイント）をバックエンドに実装した**（`backend/app/orders.py` `inventory.py` `rules.py`。画面は別）。宅配（時間枠・区画・配達員・暗証コード・模擬の配達）・ロット（賞味期限・FEFO）・通知・発注点の通知は**未実装**。

設計から変えた点・決めた細部:

- **状態遷移の表は `orders.py` の `TRANSITIONS` の 1 か所**（from, to, 許す actor）。表に無い遷移は 409。顧客の取消しだけ、表が許さないときのコードが `not_cancellable`（他は `invalid_transition`）。スタッフの取消しは `paid` から `ready` まで（`placed` は支払い前で、店の対象外）。
- **確保の期限は `stock_reservations.expires_at`**（`orders` には列を持たない）。支払い完了で NULL。期限切れ（`expire_stale`）は `placed` で確保が `held` のものを、`FOR UPDATE OF o SKIP LOCKED` で押さえて `cancelled`（reason `payment_timeout`、actor `system`）にする。呼ぶのは worker（30 秒ごと）と、注文の読み取り・確定・スタッフの一覧・在庫の一覧の前（遅延）。`pay` は自分で期限を見て、過ぎていれば取り消して 409 `reservation_expired`。
- **冪等キーの再送は、最初の応答の写しではなく、その注文の今の状態を返す。** `idempotency_keys.response` には作成時の応答を残す（注文の特定に使う）。同じキー・違う本文は 422。確定が失敗（売り切れなど）すれば、キーも確保も提案の使用済みも、すべて戻る（同じキーでやり直せる）。同じキーの並行リクエストは、先の commit まで待つ。
- **ロックの順:** 冪等キー → カート → 在庫の残高（品目 ID の昇順）→ 受け取り番号の採番（確定）。既存の注文を触る操作は、注文の行 → 確保 → 在庫の残高（品目 ID の昇順）。デッドロック（40P01）・直列化失敗（40001）は、確定だけ 3 回まで再試行する。
- **営業時間の判定:** MO 不可店と臨時休業（`store_closures`）は常に見る。定休日・営業時間・ラストオーダー・販売時間帯は `ORDER_HOURS_CHECK=off`（開発の便宜。既定 on）のとき見ない。季節の期間は常に見る。ラストオーダーの時刻ちょうど・`sold_until` ちょうどは「出せる」、閉店の時刻ちょうどは「時間外」。判定の時刻は `LOCAL_UTC_OFFSET_HOURS`（既定 9）のローカル時刻で、`business_date` も同じ。`APP_ENV=production` では、`AUTH_MODE=dev` も `ORDER_HOURS_CHECK=off` も起動を拒否する。
- **受け取り番号**は、店 × 営業日の連番（`store_order_counters` の `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`）。注文の確定の最後に採番して、ロックの時間を短くする。`public_id` は紛らわしい文字を除く 8 文字（`secrets`）。
- **ポイント:** `completed` で `floor(合計 / 100)` 点を、`loyalty_ledger`（`earn` は 1 注文に 1 回の部分 UNIQUE）と `users.loyalty_points` へ、同じトランザクションで。0 点なら台帳に書かない。失効・無料券の引き換え（`expire` / `redeem`）は表だけで、処理は未実装。
- **ログイン:** email ごとに 15 分で 5 回の失敗で 429（設計の既定。`limits.py`）。email を狙った締め出しができる（未対策。IP での制限は持たない）。
- **冪等キーの期限切れの削除**と、台帳から残高を夜間に照合する処理（`inventory.reconcile` は関数だけ。worker からは呼んでいない）は未実装。
